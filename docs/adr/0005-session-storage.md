# ADR-0005. Хранение сессий пользователей

* Статус: принято
* Дата: 2026-11-08

Контекст : приложение TimeCapsule хранило сессии пользователей файлами на диске app-server. Пока сервер один, это работает. В ЛР6 приложение запускается в группе Auto Scaling от двух до четырех серверов за балансировщиком. Если сессия лежит на диске одного сервера, пользователь, который вошел на нем, на другом сервере окажется не залогинен. Серверы группы при этом добавляются и удаляются сами, поэтому сессии не должны жить вместе с сервером.

Решение : сессии хранятся в таблице Amazon DynamoDB timecapsule-dev-sessions с ключом id типа String, в режиме On-demand и с включенным TTL по атрибуту expires. Приложение регистрирует обработчик сессий Aws DynamoDb SessionHandler до вызова session_start, имя таблицы берется из настройки SESSIONS_TABLE. Серверы получают права от роли timecapsule-dev-app-role с политикой timecapsule-dev-app-sessions, которая разрешает только GetItem, PutItem, UpdateItem и DeleteItem для этой таблицы. Ключей доступа в настройках нет.

Рассмотренные варианты :
* Хранение на сервере с привязкой сессий, то есть sticky sessions: балансировщик ставит cookie и всегда отправляет пользователя на один и тот же сервер. Ничего нового создавать не нужно. Но при удалении или замене сервера все его сессии пропадают, нагрузка распределяется неровно, а при отказе сервера пользователи теряют вход. Это плохо сочетается с автоматическим добавлением и удалением серверов.
* Таблица сессий в RDS: база уже есть, новых сервисов не нужно. Но каждый запрос пользователя создает запись в единственной базе, которая не умеет масштабироваться вместе с группой. Старые сессии приходится чистить самой. Кроме того, мою базу каждый вечер останавливает расписание, и в это время никто не смог бы войти.
* DynamoDB, этот вариант выбран: не нужны серверы, таблица масштабируется сама, TTL удаляет просроченные сессии, платежи за учебные сессии составляют доли цента. Минус в том, что это еще один сервис, а каждый запрос добавляет обращение по сети.

Последствия :
* Плюсы: любой сервер группы может обработать любой запрос, потому что сессия лежит в общей таблице, а в cookie хранится только ее идентификатор. Группа добавляет и убирает серверы без потери входа пользователей. Сервер приложения больше не хранит данные пользователей на своем диске.
* Безопасность: права у роли минимальные, только четыре действия над одной таблицей, поэтому при утечке учетных данных сервера ущерб ограничен сессиями. Ключи доступа не лежат в файлах и в репозитории.
* Стоимость: режим On-demand платит только за запросы, для учебных сессий это доли цента. Расписание остановки базы не затрагивает таблицу, так что сессии работают и ночью.
* Минусы и риски: если DynamoDB станет недоступна, пользователи не смогут входить, потому что каждый запрос читает сессию. Каждое обращение к странице добавляет несколько миллисекунд на сетевой запрос. TTL удаляет просроченные элементы не сразу, а в течение нескольких дней, поэтому срок жизни сессии дополнительно проверяет сам обработчик.
* Что изменится при нескольких серверах: ничего менять в приложении не нужно, любые новые серверы из образа сразу работают с той же таблицей. Образ нужно создавать только после выкладки версии с DynamoDB, иначе новые серверы будут хранить сессии в файлах и вход начнет теряться.
