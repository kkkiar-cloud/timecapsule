# ADR-0003. Хранение вложений пользователей

- Статус: принято
- Дата: 2026-10-21

## Контекст

В предыдущей лабораторной файлы пользователей хранились на диске сервера приложения. Это не очень удобно, потому что при удалении сервера можно потерять файлы. Кроме того, если в будущем будет несколько серверов, на каждом из них могут находиться разные файлы. Нужно выбрать такое хранилище, чтобы вложения не зависели от одного сервера и были доступны приложению независимо от того, на какой сервер пришёл запрос пользователя.

## Решение

Для хранения вложений выбран Amazon S3. Файлы хранятся в бакете timecapsule-dev-uploads-kkkiar в регионе eu-central-1, в папке (префиксе) uploads/. Приложение загружает файлы и получает к ним доступ через AWS SDK, используя IAM-роль сервера. Для скачивания файла пользователь получает подписанную ссылку, которая действует 5 минут. Перед созданием ссылки приложение проверяет, имеет ли пользователь право получить этот файл. В бакете включено версионирование, а для старых версий настроено правило жизненного цикла.

## Рассмотренные варианты

- **Диск EBS сервера приложения:** самый простой вариант, если сервер только один. Не нужно настраивать отдельное хранилище. Но файлы находятся на диске сервера, и при его удалении или неправильной настройке можно их потерять. Если появятся другие серверы, придётся решать, как передавать файлы между ними.

- **Общая файловая система Amazon EFS:** несколько серверов могут работать с одними и теми же файлами. Это удобно при масштабировании, потому что не нужно копировать вложения на каждый сервер. Но EFS требует дополнительной настройки и может обходиться дороже для нашего проекта.

- **Amazon S3 (выбран):** файлы хранятся отдельно от серверов, поэтому их не нужно переносить при замене сервера. Можно выдавать временные ссылки на скачивание, включить версионирование и настроить автоматическое удаление старых версий. Этот вариант подходит для вложений TimeCapsule и позволяет в будущем добавить другие серверы без переноса файлов между ними.

## Последствия

- **Плюсы:** файлы хранятся отдельно от сервера приложения. Если сервер удалить или создать заново, вложения в S3 останутся на месте. Для доступа к бакету используется IAM-роль, поэтому не нужно записывать постоянные AWS-ключи в код приложения.

- **Получение файлов:** когда пользователь хочет скачать вложение, приложение проверяет его права и создаёт подписанную ссылку. Ссылка действует 5 минут, после чего для скачивания нужно получить новую. При этом приложение должно снова проверить права пользователя. Так файл не приходится делать общедоступным.

- **Защита от удаления:** в S3 включено версионирование. Если объект удалить обычным способом, создаётся маркер удаления, а предыдущая версия остаётся в хранилище. Это позволяет восстановить файл, если он был удалён случайно. При этом старые версии тоже занимают место.

- **Расходы на хранение:** чтобы старые версии не накапливались бесконечно, настроено правило жизненного цикла: версии старше 90 дней удаляются, но две последние неактуальные версии сохраняются. Это помогает ограничивать расходы. Также нужно учитывать объём файлов и количество запросов к S3.

- **Если серверов станет несколько:** перед серверами можно будет поставить балансировщик нагрузки, который будет распределять запросы пользователей. Все серверы смогут обращаться к одному бакету S3, поэтому не придётся копировать вложения между серверами. Какой бы сервер ни обрабатывал запрос, он сможет получить нужный файл из общего хранилища.

- **Минусы:** нужно правильно настроить права доступа и правила хранения. За S3 нужно платить в зависимости от использования, а при неправильной настройке старые версии могут занимать лишнее место. Подписанные ссылки имеют ограниченный срок действия, поэтому после его окончания потребуется получить новую ссылку.
